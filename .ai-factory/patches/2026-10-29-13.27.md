# Librarian runner settings live refresh

**Date:** 2026-10-29 13:27
**Files:** `web/lib/librarian/stream.ts`, `web/components/librarian/librarian-provider.tsx`, `web/components/librarian/librarian-panel.tsx`, `web/lib/librarian/__tests__/turn.integration.test.ts`, `web/app/api/librarian/__tests__/routes.integration.test.ts`, `web/e2e/librarian-acceptance.spec.ts`, `docs/api/async/librarian-stream.asyncapi.yaml`
**Severity:** medium

## Problem

An open librarian panel retained stale availability after an administrator
saved a different runner. Sending appeared to require restarting the platform.

## Root Cause

The durable conversation SSE loop observed messages and turns, but did not
observe platform librarian settings or the selected runner catalog entry.
The provider therefore never requested a fresh conversation view after a
configuration or readiness change. Runner selection itself was already correct:
real saves and captured session-create payloads proved that starts resolve the
current runner, including changes to model and environment under the same id.

## Solution

Compare current settings and selected runner in the existing server read loop.
Emit a content-free settings pointer on connect and on changes, independently
of conversation existence or message sequence. The provider uses its existing
refresh tick; an older overlapping HTTP read cannot overwrite newer state.
No runner configuration enters the SSE payload and no client polling is added.

## Prevention

- Audit both the durable writer and the live reader for settings changes.
- Assert executor/model and runner identity in actual session-create payloads;
  absence of resumeSessionId alone does not prove which runner launched.
- Preserve context, memory and drafts across refreshes; test queued and admitted
  messages against settings at start, while an active answer finishes unchanged.
- Await automatically dispatched successor turns explicitly in integration tests;
  the request's original promise does not own background after-commit work.
